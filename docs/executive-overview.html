The problem we are solving

🔍
No single source of truth
There is no reliable answer to "what version of X is running in production right now, who approved it, and what validation did it pass?" Information lives in Slack threads, JIRA tickets, and individual engineers' heads.
🤝
Release coordination is manual
Cross-team releases depend on email chains and ad-hoc Slack coordination. Approvals are unstructured, non-binding, and leave no audit trail. A missed sign-off is invisible until something goes wrong.
🔐
Validation is inconsistent
Each team runs its own checks in its own way. There is no guarantee that a release has passed the right validations before it reaches production. Outcomes are not recorded systematically.
⏱️
Releases block on humans
Validation steps that could be automated run manually, on different schedules, by different people. Teams wait for sign-offs they don't fully understand. Release velocity is throttled by process friction.

What ReleaseDB is

ReleaseDB is an inter-team release coordination layer that sits above existing CI/CD tooling. It records what was built, how it was validated, who approved it, and where it was deployed — creating a permanent, queryable audit trail for every release in the organisation.

It does not replace — it sits above
↗
CI/CD pipelines — or none at all Builds happen wherever they happen. ReleaseDB accepts registrations from any script, pipeline, or tool via REST API or Python client. No specific CI system is required.
↗
Artifactory / S3 / registries Artifacts are still stored in existing systems. ReleaseDB tracks metadata and provenance, not binaries.
↗
Deployment tooling Deployments still run via existing mechanisms. ReleaseDB records the outcome and links it to the release.
↗
JIRA / ticketing Release notes and ticket links are captured as custom metadata fields — not managed by ReleaseDB.

Team configures once
Teams define their release shape, required metadata fields, and which validation scripts must pass — all in a YAML file checked into their repository. ReleaseDB enforces it automatically on every release.
Validation is automated and recorded
Validation scripts run in Docker containers. Results — pass, fail, warn — are stored with full stdout/stderr. Blocking validations prevent advancement. Non-blocking validations warn without halting.
Every action is an immutable event
Every state change — artifact registered, validation passed, approval given, deployment started — writes an immutable event row. This log cannot be altered. It is the compliance record.

Key capabilities

🔬
Configurable per-team release types
Each team defines their own release shape: artifact count, versioning scheme, required metadata, and which file types are permitted. Firmware, services, and libraries each follow their own rules.
✅
Automated validation gates
Teams register Docker-based validation scripts that run automatically on every release. Blocking validators prevent advancement; non-blocking ones record warnings. Results are stored with full evidence.
🖊️
Structured approval workflows
Approvals are captured per-release, per-environment, per-team. Each approval records the approver's identity, decision, comment, and timestamp. Approval workflows are optional — enabled per release type and environment via the requires_approval flag.
🔗
Full artifact provenance
Every artifact records the git commit, CI run URL, build tools (name + version + git SHA), and a cryptographic manifest digest. Answer "exactly what produced this binary?" in one query.
📜
Immutable audit log
Every event — artifact registered, validator run, approval given, deployment started — is appended to an immutable log enforced at the database level. Nothing is ever updated or deleted.
🛠️
Config-as-code team onboarding
Teams onboard by committing a releasedb.yaml file to their repository. One command syncs their configuration to the platform. No UI forms to fill in.

Engineering Leadership
  • See what is running in every environment at any time
  • Know that every production release was approved by an authorised person
  • Track release velocity and validation pass rates across teams
Team Leaders
  • Define their team's release rules once in a YAML file
  • See all pending approvals in one place
  • Approve or reject with a comment — recorded permanently
  • Get notified when a release is ready for sign-off
  • Delegate approval to specific individuals per environment
Engineers
  • Register artifacts via REST API, Python client, or plain curl — no CI system required
  • Write validation scripts using the optional Python SDK
  • Test validators locally with one command, no live API needed
  • See exactly which checks passed or failed and why
  • No new tools to learn beyond a YAML config and an HTTP call
Platform team maintains ReleaseDB itself — the database, API, and runner infrastructure. All other teams are users of the platform with zero infrastructure responsibilities.
Auditors / Security get a read-only API and dashboard view. No access to underlying systems required. Evidence export is a single API call.

How a team adopts ReleaseDB

Day 1
Copy the config template
The team copies releasedb.template.yaml into their repository, fills in their team slug, and defines their first release type with required metadata fields. This file is reviewed and merged via a normal pull request.
Day 2
Sync configuration to the platform
One command — releasedb-sync --dry-run — previews every change before applying. The team runs releasedb-sync to register their team, release types, and field definitions. This can be run manually, from a CI step, or from any script — wherever is convenient.
Week 1
Write and register validation scripts
Engineers write validation scripts using the Python SDK and test them locally with releasedb-validate --dry-run. Scripts are uploaded to S3, their checksums recorded in releasedb.yaml, and synced to the platform.
Week 2
Register artifacts and trigger validation
Two API calls complete the integration: one to register the artifact after build, one to trigger and gate on validation before promotion. These can come from a CI pipeline step, a post-build script, or any tool that can make an HTTP request — curl, the Python client, or any HTTP library.

Open design decisions

Canonical release marking
Should a release be explicitly marked as "the current stable version" independently of its lifecycle status? Required when external systems (registries, deployment tools, release notes pages) need to resolve "the release" by a stable name.
Options: rely on status = deployed (no schema change), add is_canonical flag on releases, or a release_tags table (stable, lts, latest).
Artifact dashboard
A read-only view of artifacts, lineage, validation status, and provenance. Should this be built bespoke or use an off-the-shelf tool?
Options: Retool (fastest to value, no frontend code), or bespoke FastAPI + HTMX (~300 lines, fully owned). Metabase / Grafana are weaker fits.
Operations web UI scope
Five pages covers all human-centric workflows: dashboard (pending approvals), release list, release detail (validations + approvals + events), approval action, tool registry. Retool delivers this in a day; a bespoke view takes a sprint.
Authentication model
The API currently uses bearer tokens. Production will require SSO integration (Okta / Azure AD) so that approver_identity is a verified user identity, not a self-reported string.
ReleaseDB
One platform. Every release. Full provenance, automated validation, structured approvals, and an immutable audit trail — without replacing a single tool teams already use.
